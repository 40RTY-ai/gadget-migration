How it works

The principle: change where the code runs, never what it does.

Same code

Each Gadget package resolves to a stand-in by import alias. No rewrite of your routes, actions or React hooks.

One store at a time

A front door proxies unmoved stores to Gadget. Each store moves in a few seconds and can move back in one click.

Any cloud

The playbook names services by role (runtime, Postgres, queue, cron, KMS), so you can fill each one from GCP, AWS, Azure or a small host.

Nine phases, each with a gate

Your app keeps working at the end of every phase.

  1. InventoryCount which Gadget features you use and prune the rest
  2. Landing zoneRuntime, private Postgres with PITR, queues, secrets
  3. Stand-insExisting test suite passes on the new runtime
  4. Schema + jobsGadget ids kept as keys; queue lanes match
  5. BridgeGadget-side routes for rows, tokens, billing
  6. Front doorNew installs land on your cloud
  7. Store moveCopy, token hand-off, webhooks, flip
  8. Waves~6 stores at a time, auto-pause on failures
  9. Decommission0 outbound Gadget calls, then delete
